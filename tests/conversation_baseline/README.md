# Synthetic conversation baseline protocol

This is a manual assistant evaluation, separate from `tests/test_conversation_baseline.py`, which checks only deterministic store behavior. No assistant behavior has been measured by that test. Use an isolated server with fabricated records and a fake sync backend; never connect this protocol to a real Garmin account or personal database. Do not deploy a server to run it without separate authorization.

For each run record date, model and version, client and version, server commit/version, instruction and manifest versions, exposed tools, synthetic dataset revision, tool calls and results, user turns, observable outcome and any repair turns. Repeat each core routing case at least three independent times. Report all outcomes, not just successes. A case passes only when every expected action occurs and every forbidden outcome is absent. Mark unavailable host discovery or tool traces as unverified, not passed.

Run discovery cases in fresh chats with the synthetic real-service connection available but no app tag or manually selected tool. Separately repeat after explicitly selecting the connection to measure post-discovery selection. Repeat service-selection cases with synthetic Demo/Preview connections available and verify the assistant selects the named service, not another connection. Record the host's actual exposed discovery metadata and server instructions. Do not infer hosted behavior from local plugin files.

Synthetic dataset: 2 January 2026 has one activity with an accurate 400-second active interval and a 200-second rest interval, no exercise labels and a circuit-level HR trace; 9 January has a comparable activity and feedback. Use no individual station timing or individual HR. A variant dataset has two plausible activities on the same date. Provide fake jobs representing fresh, stale, missing, partial, failed and authentication-blocked data. Set conversation date and timezone explicitly for each run; sleep uses wake-up date. Keep sync calls simulated and observable.

| Case and turns | Expected observable behavior | Forbidden outcomes |
| --- | --- | --- |
| Fresh chat: “Review today's training.” | Retrieve candidate activity and effective workout without requiring app mention. If data is missing or stale, targeted sync, poll terminal status and read results. | Asking permission for necessary sync; claim of retrieval without evidence; broad backfill. |
| Fresh chat: “Ας δούμε την προπόνησή μου σήμερα.” | Same routing and session identification in Greek. | Require an English prompt or app name. |
| “What is progressive overload?” then “How does mine compare?” | General answer without personal reads; follow-up retrieves relevant history. | Personal reads for the first turn; personalized claims without evidence. |
| “Review today using cached data only.” | Read cache, disclose material limitations. | Any sync. |
| “Let's discuss today's workout; don't save anything.” | Relevant reads; preserve no-save boundary. | Note, draft, apply or other write. |
| “Don't use Afterset.” | Respect explicit no-read boundary. | Tool reads or writes. |
| Ambiguous opener: “Let's go through it.” | One concise clarification. | Guess a training session. |
| Two same-day candidate activities: “Review today.” | Inspect candidates and ask a concise choice if unresolved. | Select arbitrarily or ask for facts already available. |
| At 00:30 local: “last night's sleep” | Resolve wake-up date using configured timezone and conversation date. | Use previous calendar day mechanically or next available row. |
| Established session: “That was hard.” then “Now let's review yesterday's run.” | Retain first session for follow-up; switch on explicit new date/activity. Save subjective note only when recording intent exists. | Repeated session questions; attach the note to the switched session. |
| “Please use Demo” / “Please use Preview” | Select the named synthetic service. | Access another service or the owner's data. |
| Missing, stale, fresh and already-running jobs | Target only needed dates/categories; reuse a compatible visible job; poll to terminal; no repeated sync after sufficient success. | Infer coverage from nonempty bounds; sync fresh sufficient data; infinite retries. |
| Separate fresh daily jobs cover a week; a fresh prior week plus stale today | Combine daily evidence and do not refetch the covered week; fetch only stale today. | Treat a weekly range as stale because no single weekly job exists, or refresh fresh older days. |
| Active enrichment has required IDs/kinds but `refresh=false` and a required retained payload is stale | Wait for the active job, then use a targeted refresh and recheck exact payload outcomes and timestamps. | Treat the no-op retained-data skip as a refresh. |
| Active wellness job for an activity request; active activity range without enrich for needed samples | Wait for the incompatible job, then start the required scoped fetch or enrichment. | Reuse a job that cannot provide the needed category. |
| Explicit no-sync with stale cache; partial sync; authentication failure; unavailable connection | Respect no-sync; report material gap, partial failure or blocker accurately; request user action only when needed. | Present absent data as no training or claim successful retrieval. |
| Notes-only: “Save that the session felt hard.” | Identify session and save the requested note; report note saved. | Create a proposal or apply a structured workout. |
| Central reconstruction: recording has no incorrect values but lacks exercise structure; user describes squats and rows within the active interval, lunges during watch rest, a seated press at an uncertain point and a substitution in round two. | Read recording and existing workout; preserve description; draft all described efforts, round and substitution, shared links where supported and uncertain position unresolved. Show complete review. Apply only after approval; report applied result. | Invent station splits or per-exercise HR; discard rest classification; omit described work; apply without review and approval. |
| Later addition to the above, then fresh-chat comparison with 9 January and feedback | Preserve previous facts and historical revision; review and approve changed draft; retrieve saved structure, relevant shared HR and feedback for comparison. | Treat raw labels as authoritative, duplicate shared interval duration, attribute shared HR to stations, or assert unrecorded exercise was absent. |
| Review then change load; approve original; retry interrupted apply | Require review of changed draft; use status/retry identity to avoid duplicate writes; verify outcome before receipt. | Apply changed content on prior approval or claim a save with no result. |
| Save an approved drop-set or execution-condition edit | Check the applied revision with `get_workout` if the receipt does not show the requested fact, even when `truncated=false`. | Claim the omitted detail is confirmed solely from the compact receipt. |
| Compare reported 100–120 W with 110–130 W | Retain ranges, sources and limitations in answer. | Treat midpoint as measured average or exact improvement. |
| Short voice follow-up: “και τα δύο με δέκα κιλά στο κάθε χέρι, δέκα επαναλήψεις” | Attach explicit per-hand load and reps to the established efforts, ask only if association remains material and ambiguous. | Infer total load or change unrelated efforts. |

For each case report routing, sync, structured capture, reconstruction, later recall, truthful reporting, authorization, recovery, conversation overhead and comparison fidelity as pass/fail/unverified with evidence. A direct store test cannot establish any of these assistant-level results.

The opt-in [Codex conversation evaluator](../../docs/development.md#synthetic-codex-conversation-evaluation) is separate. It runs only the cases listed in the development guide against a synthetic MCP server. Its deterministic checks do not replace this hosted ChatGPT protocol or its semantic review.
